# Сквозной аудит Buyerly — 17 августа 2026

## Зачем сделан этот документ

Это зафиксированный снимок состояния продукта перед следующим циклом разработки. Он не заменяет [product backlog](PRODUCT_BACKLOG.md): аудит объясняет, что уже работает, где обнаружен риск и какой номер backlog закрывает этот риск.

Проверена production-версия `d4aebf1`, шесть пользовательских разделов, 30 API endpoint, 11 моделей PostgreSQL, web/API/bot/worker, маршруты Meta-клиента, фоновые циклы, 85 автоматических тестов и эксплуатационные документы. Секреты, access token и персональные значения в документ не переносились.

## Карта работающей системы

| Слой | Что уже работает | Главный следующий шаг |
|---|---|---|
| Web | кабинеты, правила и группы, сохранённая сводка, логи, добавление кабинетов, настройки; стабильные URL | полные состояния UI, E2E и расширенная аналитика |
| API | авторизация, ownership-проверки, CRUD правил, снимки/представления, действия над логами | строгая валидация, стабильная identity и документированный контракт |
| Bot | вход/регистрация, уведомления и ручные callbacks | единый AuditEvent и единая отмена с web |
| Worker | мониторинг кабинетов, расчёт правил, приоритет конфликтов, действия Meta | долговечные cooldown/idempotency и настоящий heartbeat |
| PostgreSQL | пользователи, кабинеты, правила/группы, события, остановленные объекты, снимки и настройки вида | факты аналитики, состояние выполнения правил и безопасные миграции |
| Meta client | account-level отчёт периода, пагинация, управление статусом/бюджетом | валюта, диагностируемые rate limits и расширяемый каталог полей |

## Что подтверждено как готовое

- Лиды, регистрации и покупки разделены; общий показатель «Результаты» не используется.
- CPL, CPReg и CPP при отсутствии события не подменяются расходом или нулём.
- Spend периода берётся на уровне кабинета и не исчезает из-за текущего статуса ad set.
- Последняя успешная сводка хранится в PostgreSQL и переживает обновление страницы.
- Представление таблицы сохраняет видимость, порядок и ширину колонок, поиск, фильтр, сортировку и период.
- Ширину колонок можно менять мышью; двойной клик возвращает исходную ширину.
- Разделы имеют стабильные адреса и сохраняются после reload, входа и переходов назад/вперёд.
- В одном worker-цикле над ad set выполняется одно действие с явным приоритетом конфликтов.
- CI запускает тесты перед deploy, а deploy имеет healthcheck и rollback.

## Критические находки

| Риск | Фактическое состояние | Последствие | Backlog |
|---|---|---|---|
| Повтор действия после restart | cooldown и last-checked живут только в памяти worker | повтор STOP/START или изменения бюджета после deploy | BL-006 |
| Неизвестное действие | runtime может подменить неизвестный action на STOP | некорректный payload способен остановить объект | BL-005 |
| Изменяемый ключ владельца | Telegram ID используется и как настройка профиля, и как owner ID зависимых данных | смена ID может скрыть кабинеты, правила, снимки и историю | BL-004 |
| Смешанные валюты | Meta возвращает currency, но Buyerly её не сохраняет и выводит `$` | общий Spend/CPA может быть математически неверным | BL-015 |
| Неполный аудит Telegram | callbacks меняют Meta/локальное состояние без общего AuditEvent | история web и bot расходится, отмена ненадёжна | BL-030/031 |
| Ложное ощущение здоровья | настройки показывают статичный online, readiness worker фиксирует в основном запуск | зависший worker может выглядеть здоровым | BL-050/090 |

## Проверка пользовательских разделов

### Мои кабинеты

Работает список доступных кабинетов, статусы, назначения и переход к действиям. Для реальной работы с большим объёмом не хватает фильтрации по группам/байерам/валютам, массовых назначений и результата по каждому элементу при частичной ошибке. Это BL-026. Валюта и стабильное владение закрываются BL-015 и BL-004.

### Правила

Работают одиночные правила, группы, приоритет победившего действия и основные метрики в условиях. До широкого использования нужны fail-closed валидация (BL-005), долговечная идемпотентность (BL-006), preview/режим наблюдения (BL-040), минимальная статистическая база и расписание (BL-041), а также объяснение подавленных конфликтующих правил (BL-042).

### Сводка

Текущая версия правильно разделяет воронку, сохраняет снимок и пользовательский вид таблицы. Следующий аналитический слой: валюта и атрибуция (BL-012/015), полный каталог метрик (BL-020), отдельные views/KPI (BL-021), иерархия до объявления (BL-022), графики и воронка (BL-023), breakdown (BL-024), регулярное fact-хранилище (BL-025). До BL-025 live-обновление растёт по времени вместе с числом кабинетов, потому что API собирает данные Meta во время запроса.

### Логи

История существует, но продуктовые состояния всё ещё оформлены как очередь подтверждения. По принятому решению успешное действие должно сразу быть «Выполнено», а доступная операция — «Отменить». Нужно объединить события worker/web/Telegram, хранить before/after и correlation ID (BL-030), затем добавить проверяемую идемпотентную отмену без переписывания истории (BL-031).

### Добавление кабинетов

Пакетное добавление работает, но дальнейшее управление большим набором требует групп, bulk-операций и прозрачных частичных ошибок (BL-026). Состояние/срок действия Meta-доступа должно диагностироваться без публикации самого token (BL-012/073).

### Настройки

Есть профиль и описание мониторинга, но статус online не доказывает работу полного worker-цикла. Нужны фактические heartbeat API/bot/worker/database, начало/конец последнего цикла и состояние по кабинетам (BL-050/090). Смена Telegram ID должна быть отделена от ownership (BL-004). Web-сессии и хранение Meta token требуют усиления (BL-073).

## Сквозные проблемы качества

### Производительность и рост

Сводка сейчас подходит для небольшого числа кабинетов, но её live-обновление зависит от последовательных внешних ответов. BL-025 переносит синхронизацию в worker, хранит нормализованные факты и оставляет API быстрым чтением из PostgreSQL. BL-022 добавляет виртуализацию/пагинацию для больших таблиц.

### Доступность и адаптивность

Контрактные frontend-тесты проверяют наличие элементов в исходниках, но не реальное поведение браузера. Не хватает focus trap и корректной семантики диалогов, полной keyboard-навигации, проверок 200% zoom, длинных значений и мобильных состояний. Это BL-052 и BL-090.

### Роли и изоляция

Роли admin/buyer есть, но административный контекст и управление правилами другого владельца не образуют законченный командный сценарий. Нужны viewer, явный выбранный владелец, передача кабинета и полный аудит административных действий. Это BL-004 и BL-072.

### Документация

Основные README, архитектура и deploy-инструкция отражают текущую систему. Одновременно в репозитории остаются старые материалы с SQLite, общей CPA и примерами, где стоимость события при нуле может считаться неверно. Перед обучением сотрудников их нужно архивировать или переписать, затем собрать единое оглавление и проверку документации. Это BL-080—084.

## Принятая последовательность

Сначала устраняются риски необратимых Meta-действий: BL-006 и BL-005. Затем интерфейс истории приводится к модели «выполнено → при необходимости отменить» через BL-030/031. После этого стабилизируются ownership, валюта и heartbeat (BL-004/015/050), и только затем наращиваются каталог метрик, хранилище, иерархическая таблица и графики.

Каждое изменение выпускается отдельным коммитом: тесты → push в `main` → production deploy → проверка версии/health → ручная проверка затронутого сценария → обновление backlog.
