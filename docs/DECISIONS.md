## Запись №14: Каноническая дедупликация событий Meta Insights
* **Дата:** 16.08.2026
* **Проблема:** Meta Insights API отдает в массиве `actions` параллельно агрегированные события (`lead`, `complete_registration`, `purchase`) и пиксельные события (`offsite_conversion.fb_pixel_...`), из-за чего цифры удваивались.
* **Решение:** Внедрен канонический парсинг `actions_dict` со строгой приоритезацией стандартных событий без дублирования.

## Запись №15: Безопасный режим добавления кабинетов (Правила выключены по умолчанию)
* **Дата:** 16.08.2026
* **Требование заказчика:** Не назначать автоправила сразу при добавлении кабинета. Дать возможность использовать бота только для статистики и расходов без вмешательства воркера.
* **Решение:** Колонка `rules_enabled = Column(Boolean, default=False)`. Индивидуальный тумблер в карточке кабинета. Воркер оценивает стопы только при `rules_enabled == True`.

## Запись №20: Техническое усиление (Hardening) Meta API клиента и воркера
* **Дата:** 16.08.2026
* **Статус:** Реализовано, покрыто тестами.
* **Решение:**
  * Внедрен метод `_request_with_retry` с умным Exponential Backoff + Jitter (2с $\rightarrow$ 4с $\rightarrow$ 8с) для защиты от временных сбоев Meta и ошибок 429/5xx.
  * Реализован парсер заголовка `X-Business-Use-Case-Usage` для превентивного отслеживания исчерпания BUC-лимита $>80\%$.
  * Внедрен межаккаунтный случайный джиттер `0.5–1.5 сек` в цикле воркера для сглаживания сетевой нагрузки.

## Запись №21: Разделение production-сервисов и PostgreSQL
* **Дата:** 17.08.2026
* **Статус:** Реализовано.
* **Проблема:** API, статический веб, Telegram polling и фоновые задания работали в одном процессе с общей SQLite-базой. Сбой или перезапуск одного контура затрагивал весь продукт.
* **Решение:** Выделены сервисы `web`, `api`, `bot`, `worker` и `db` (PostgreSQL 16). Добавлен одноразовый транзакционный перенос SQLite, раздельные журналы процессов, healthcheck API/web и автоматический возврат предыдущих образов.
